# ML54-01 — Contrato de cenários

Este contrato cobre a remoção da falsa classificação de links afiliados e a persistência do
fallback por oferta. A tarefa não gera, importa ou valida link oficial do Mercado Livre.

## Shape obrigatório do resultado

Cada resolução deve devolver exatamente as dimensões que os consumidores precisam para não
inferir atribuição a partir de uma tag ou do formato da URL:

```ts
type OfferUrlResolution = {
  url: string
  destination: 'untracked_fallback'
  origin: 'none' | 'legacy_manual'
  validation: 'absent' | 'unverified' | 'rejected'
  reason:
    | 'fallback_absent'
    | 'fallback_unverified'
    | 'fallback_url_invalida'
    | 'fallback_protocolo'
    | 'fallback_dominio'
    | 'fallback_wid'
}

type OfferUrlCounters = {
  fallback: number
  fallback_absent: number
  fallback_unverified: number
  fallback_url_invalida: number
  fallback_protocolo: number
  fallback_dominio: number
  fallback_wid: number
}
```

`fallback` é exatamente a soma de `fallback_absent`, `fallback_unverified`,
`fallback_url_invalida`, `fallback_protocolo`, `fallback_dominio` e `fallback_wid`. Os motivos de
formato, protocolo, domínio e `wid` identificam uma entrada manual rejeitada; eles incrementam
`fallback` e não podem ser confundidos com `fallback_unverified`, que representa uma URL legada
manualmente fornecida, sintaticamente aceitável, mas sem proveniência oficial. Uma entrada
inexistente ou string vazia é `absent`; uma string não vazia que não seja URL válida é `rejected`
com `fallback_url_invalida`. Não existe `tracked` nem `sem_tag_de_afiliado` no tipo, nos
contadores, em `result.urls`, nos logs ou em qualquer resposta do cron.

Para esta tarefa toda resolução tem `destination: 'untracked_fallback'`. `origin: 'none'` e
`validation: 'absent'` significam que não havia candidato; `origin: 'legacy_manual'` e
`validation: 'unverified'` significam que havia URL manual sintaticamente aceitável, mas nenhuma
prova oficial; `origin: 'legacy_manual'` e `validation: 'rejected'` significam que a entrada
manual foi recusada por formato, protocolo, domínio ou vínculo `wid`. O fallback nunca inclui
`affiliate` e conserva exatamente um `wid` igual ao `external_id`.

O mapeamento de validação é fechado: ausência de chave ou valor `''` → `absent` /
`fallback_absent`; URL HTTPS de host aceito com `wid` correto, porém sem evidência → `unverified`
/
`fallback_unverified`; string não vazia que não parseia → `rejected` / `fallback_url_invalida`;
protocolo diferente de HTTPS → `rejected` / `fallback_protocolo`; host fora da allowlist →
`rejected` / `fallback_dominio`; `wid` ausente, divergente ou ambíguo → `rejected` /
`fallback_wid`.

## Podados

- Não foi criado cenário para candidato oficial, allowlist, redirect, DNS, timeout, 429/5xx,
  evidência de conta, inventário ou clique: pertencem às ML54-02/ML54-03 e estão fora da entrega
  independente ML54-01.
- Não foi criado cenário separado para `/go/[offerId]`: esta tarefa não muda o redirect público;
  testar isso duplicaria o contrato de ML54-03.
- Casos GET e POST do cron foram colapsados em uma tabela no mesmo cenário, pois o handler já
  possui comportamento comum; os testes existentes de 401/503/500/partial continuam sendo
  preservados e apenas o happy path com o novo retorno é ampliado.
- Casos de MLB e MLBU, codificação e unicidade de `wid` foram colapsados em uma tabela porque
  exercitam a mesma regra de builder.
- `buildMlLink` pode ser removido por não ter consumidor de produção identificado. Se for mantido
  por compatibilidade, deve deixar de acrescentar `affiliate` e seguir o mesmo fallback sem
  afiliação; nenhum cenário autoriza preservar a semântica antiga.
- A propriedade é mantida porque cobre entradas não enumeradas de codificação e identidade; a
  lane precisa configurar um gerador/property runner compatível antes do gate. O repositório não
  tem fast-check/Stryker configurados hoje, portanto essa ausência é um bloqueio de gate, não um
  passe implícito.

## Lacunas e limites do contrato

O critério documental é satisfeito por um checklist manual rastreável no diff, pois não define
uma função executável sem acoplar a documentação a um teste de implementação. O gatekeeper deve
registrar a conferência dos três arquivos e verificar que nenhuma afirmação diz que preencher
`ML_AFFILIATE_TAG` restaura atribuição.

O SQL deve ser executado em PostgreSQL isolado após as migrations atuais. Os asserts devem usar
mensagens/identificadores únicos dentro de `0011_ml_fallback_reconciliacao.test.sql`, sem inventar
funções de teste. Para isolar a URL, o fixture de simulação e o snapshot real devem compartilhar
os mesmos valores de preço, disponibilidade e ranking; não se deve falhar por `fetched_at` ou por
uma atualização legítima do histórico do dia.
